Introduction to CUTLASS for cuda.coop Developers#

This page is for developers who work on cuda.coop.cutlass and have not used CUTLASS or its Python DSL before. It explains what CUTLASS is, how the CuTe DSL turns a Python function into a GPU kernel, how that differs from other Python compilers you may know, and which of its mechanisms cuda.coop.cutlass relies on. The Developer Guide then follows one primitive through the implementation, and Minimal CuTe DSL Integration Example shows every integration point in a single file with no cuda.coop abstractions.

Paths to CUTLASS DSL modules below are relative to the installed cutlass package, for example site-packages/nvidia_cutlass_dsl/dsl_packages/cutlass or python_packages/cutlass depending on the wheel. Paths to our modules are relative to python/cuda_coop_cutlass/cuda/coop/cutlass. The DSL is distributed under NVIDIA’s EULA, so read its sources for understanding but do not copy them into this repository.

What CUTLASS is, and which part we use#

CUTLASS is NVIDIA’s open-source C++ template library for GEMM and related kernels. Its lower layer, CuTe, is an algebra of layouts and tensors that describes how threads and data map onto each other. cuda.coop.cutlass does not use the C++ library. CUB, the library that cuda.coop wraps, is a separate CCCL library.

Since CUTLASS 4, the same project ships a Python front end, the CUTLASS DSL or CuTe DSL, in the nvidia-cutlass-dsl wheel. You write GPU kernels as decorated Python functions, and the DSL compiles them through its own MLIR distribution to a cubin that it also launches. This Python layer is the only part of CUTLASS that cuda.coop.cutlass depends on. When this documentation says CuTe, CuTe DSL, or the CUTLASS compiler, it means this Python-plus-MLIR toolchain.

The wheel installs one top-level package, cutlass, with these parts:

cuda.coop.cutlass adds one thing to this toolchain: CUB device code reachable from a CuTe kernel, with the kernel’s launch shape, scratch, and synchronization requirements handled for the caller.

A CuTe kernel, piece by piece#

The kernel from Minimal CuTe DSL Integration Example is small enough to read whole:

@cute.kernel
def sum_block(source: cute.Pointer, destination: cute.Pointer):
    tidx, tidy, _ = cute.arch.thread_idx()
    rank = tidx + tidy * _BLOCK[0]
    inputs = cute.make_tensor(source, cute.make_layout(_THREADS))
    output = cute.make_tensor(destination, cute.make_layout(1))
    total = block_sum(inputs[rank])  # 1. Traced like any other CuTe call.
    if rank == 0:
        output[0] = total


@cute.jit
def launch(source: cute.Pointer, destination: cute.Pointer):
    sum_block(source, destination).launch(grid=1, block=_BLOCK)

@cute.kernel marks a GPU kernel and @cute.jit marks a host function that CuTe compiles. Calling the kernel inside the host function returns a launcher; .launch(grid=..., block=...) emits the kernel into the module and emits the launch. cute.compile(launch, source, destination) returns a compiled callable for those argument types, which is then called with matching arguments. Calling launch(...) directly compiles and runs in one step.

Inside the kernel, cute.arch.thread_idx() returns three cutlass.Int32 values, cute.make_tensor wraps a pointer in a layout, and indexing a tensor loads or stores one element. block_sum is the function this example adds; it is an ordinary Python function and the DSL has no special knowledge of it. How the DSL compiles a function#

The DSL compiles by tracing: it runs your Python function with symbolic arguments and records the operations that run. The run happens in three steps that matter to us.

Step 1: a source-level rewrite of control flow#

On the first call of a decorated function, BaseDSL.run_preprocessor fetches its source with inspect, parses it into a Python AST, and runs DSLPreprocessor, an ast.NodeTransformer in base_dsl/ast_preprocessor.py. The transformer leaves ordinary statements alone and rewrites control flow:

  • for i in range(...) and cutlass.range(...) become a staged loop that emits scf.for, even with Python integer bounds. Variables assigned in the body become loop-carried values. cutlass.range_constexpr(...) stays a Python loop, so the body is traced once per iteration and the result is unrolled code.

  • if and while whose condition is a DSL value become scf.if and scf.while with scf.yield of every variable the branches assign. cutlass.const_expr(x) asserts that x is a Python value, so the branch is decided at trace time and only one side is traced.

  • and, or, and conditional expressions on DSL values are rewritten so that Python’s short-circuiting does not silently drop the dynamic operand.

  • return, break, continue, and raise inside staged control flow are rejected with a diagnostic by this preprocessing mode.

The rewritten AST is compiled and swapped into the function object’s __code__. The rewrite happens once per function and preprocessing mode; it is not repeated on later calls. So yes, the DSL still analyzes the AST, primarily to stage control flow; it also rewrites selected Python calls and expressions. It does not type-check the function or decide which operations are legal; that happens in step 2.

Step 2: execution with symbolic values#

BaseDSL.generate_original_ir creates an ir.Module, a gpu.module for kernels, and a host func.func whose block arguments stand for the non-Constexpr parameters. It wraps those arguments in the DSL’s Python types and then simply calls the rewritten Python function with them. Every operation on a DSL value emits MLIR at ir.InsertionPoint.current. Every Python-only value behaves as it would in plain Python. When the function returns, the module contains the full program.

Two consequences shape everything cuda.coop.cutlass does:

  • Any Python function called in the body runs at trace time. A call to coop.load is not intercepted by the DSL; it executes, inspects its arguments, and emits IR itself. There is no typing registry or lowering table to register with, as there is in Numba.

  • The kernel body is traced inside the launch. KernelLauncher.launch in cutlass_dsl/cutlass.py receives the grid and block, attaches them to the kernel operation as the cutlass_launch_facts attribute, and only then traces the kernel body. Code running in the body can therefore read the exact launch shape through cute._get_launch_facts(). A dimension that is a DSL value rather than a Python integer is absent from the facts.

The example kernel’s if rank == 0 illustrates the two steps together. Because rank is a DSL value, step 1 rewrote the statement and step 2 emitted this:

%9 = arith.cmpi eq, %6, %c0_i32_9 : i32
%10 = scf.if %9 -> (!memref_gmem_i32_1) {
  cute.memref.store(%view_6, %coord_13, %8) : (...) -> ()
  scf.yield %view_6 : !memref_gmem_i32_1
} else {
  scf.yield %view_6 : !memref_gmem_i32_1
}

Step 3: finalize, hash, compile, link, run#

After the body returns, generate_original_ir runs the registered trace-finalize hooks with hook(dsl, module, function_name). A hook may inspect or change the finished module. Only then does the DSL compute the module hash that keys its JIT cache. If a cached compilation exists for that hash, it is reused; otherwise the module goes through the compile pipeline (lir-to-cute-dsl, cute-to-nvvm, and the LLVM backend), device code is linked with nvJitLink, and the result is loaded as a JitCompiledFunction and executed. Just before compiling, the DSL merges each gpu.module’s link-libraries attribute into its LinkLibraries compile option, which is how externally compiled device code reaches the device link.

Because the cache key is the traced module, a direct call always traces again, even on a cache hit. Tracing is how the DSL learns whether the program changed. cute.compile returns the compiled callable, so calling that object launches without tracing. Our tests and examples use cute.compile when they need to separate compilation from execution.

How this differs from Dynamo, Numba, and Triton#

A common first question is whether CuTe traces the way PyTorch Dynamo does. It does not, and the differences matter when deciding where to hook in.

System

What it analyzes

How it captures a program

How it reuses a compilation

PyTorch Dynamo

CPython bytecode, intercepted through the frame evaluation API before a frame runs.

Symbolically interprets bytecode into an FX graph; unsupported code causes a graph break and falls back to eager Python.

Guards on argument properties; when they pass, the compiled graph runs without re-executing the Python.

Numba CUDA (numba-cuda)

CPython bytecode, lifted to Numba IR and type-inferred.

Compiles the whole function per argument type signature; unsupported operations are typing errors. Extensions register typing templates and lowering functions.

Dispatch on argument types to a previously compiled specialization.

Triton

The function’s AST.

A code generator visits the AST and emits Triton MLIR without running the body; tl.constexpr arguments specialize.

Cache keyed by signature, constexpr values, and options.

CuTe DSL

The AST, primarily for control-flow staging; then the running program.

Rewrites staged control flow, then executes the Python body with symbolic values. Unsupported operations raise during execution. Everything in the body is captured; there are no graph breaks.

Re-traces on every direct call and looks up the module hash; or reuses the callable returned by cute.compile.

For cuda.coop the practical differences are these. There are no guards, so a primitive can read any Python-level fact it wants at trace time and the DSL will not try to generalize over it; our planners use that to specialize on the exact block shape and dtype. There are no graph breaks, so a primitive must emit valid IR or raise; it cannot defer to the interpreter. And unlike Numba extensions that use typing templates and lowering registrations, our CuTe integration needs no typing or lowering registration. coop.load is simply a function that is called during tracing.

PyIR, an optional second preprocessing mode#

The CUTLASS 4.9 candidate adds PyIR, enabled with CUTE_DSL_ENABLE_PYIR=1 or CuTeDSL.enable_pyir() and off by default. PyIRDSLPreprocessor extends the AST rewrite to put the function into SSA form, the trace emits pyir dialect operations, and the compile pipeline lowers them with pyir-prelower and convert-pyir-to-scf. The preprocessing mode is part of the cached rewrite’s identity, so switching modes re-runs the rewrite.

The primitive entry points do not perform control-flow staging, but that does not establish support for every preprocessing mode. In particular, the TempStorage.release() lifetime analysis recognizes scf and cf operations at trace finalization, before PyIR is lowered. The integration described here uses the default preprocessing mode; PyIR needs separate qualification, including storage lifetimes across control flow.

Entry points are ordinary functions#

coop.load, coop.reduce, and the other public functions validate their Python arguments, plan the CUB specialization, and emit IR, all while the user’s kernel is being traced. Nothing is registered with the DSL before the first call. To find the trace they belong to, they walk from ir.InsertionPoint.current.block.owner through parent operations to the enclosing builtin.module; to find the kernel that owns their scratch, they stop at the kernel operation, which in the 4.9 candidate is an lir.func carrying the gpu.kernel attribute. BundleSession in _compiler/_state.py keeps per-trace state keyed by the DSL’s compile options object and that module, so nested @cute.jit calls and several kernels in one module stay separate.

Launch facts#

CUB block primitives are templates on the block shape, and warp primitives need to know how many complete warps a block holds. The planner therefore requires the exact dimensions, which _compiler/_launch.py reads through cute._get_launch_facts() and records with their provenance. The nvvm.reqntid attribute also specifies an exact block shape, whereas maxntid supplies only an upper bound. This integration uses the launch facts API as its planning contract rather than inferring facts from those lower-level attributes. An exact shape alone does not establish uniform participation at a primitive call. See Exact launch facts.

Calls through the FFI#

cute.ffi(name=..., params_types=[...], return_type=...) returns a callable that, when invoked with DSL values, declares a private function prototype in the enclosing gpu.module if needed and emits func.call. Parameter and return types are DSL numeric types or MLIR types. A cute.Pointer argument is converted to !llvm.ptr automatically, and a pointer in a specific address space is cast to the generic address space when the prototype declares one. The symbol is used verbatim, which is why generated wrappers are extern "C" and why request objects derive deterministic symbol names from their plan.

Load returns several values per thread. The lowering allocates a register tensor with cute.make_rmem_tensor, passes its .iterator.llvm_ptr as a result-buffer argument, and after the call reads the elements back into the ThreadData payload. The DSL also offers cute.extern, a decorator that mangles symbol names from argument types; we do not use it because our symbol identity must include the CUB plan, not only the Python types.

The trace-finalize hook#

register_trace_finalize_hook is persistent for the DSL instance and ignores duplicate registrations. cuda.coop.cutlass registers one dispatcher and points it at the current finalizer, so repeated imports or activations never accumulate callbacks. The hook runs for every trace, so it first checks whether a session exists for the module it was given and returns if not. For a session with requests, it renders all wrappers into one C++ translation unit, compiles them with NVRTC to LTO-IR, materializes deferred scratch, and attaches the artifact path to each gpu.module.

The DSL’s own module hash runs after the hook and includes the module’s attributes, so a different bundle path changes the hash. Our bundle cache in _compiler/_cache.py keys on the rendered source, header identity, compiler options, and architecture, so a repeated kernel finds the same .ltoir file and the DSL’s cache hits as well.

LTO-IR and the device link#

NVRTC compiles the wrappers with --relocatable-device-code=true and -dlto and we store the LTO-IR container in a cache directory. The DSL documents its link-libraries mechanism in terms of LLVM bitcode, but its compiler recognizes LTO-IR containers as nvJitLink inputs and links them with the kernel’s own LTO-IR. The link can inline the wrapper into the kernel; the runtime tests confirm with cuobjdump that no call or provider symbol remains in the final cubin.

The CUTLASS 4.9 candidate copies compile options for each invocation, so adding a module’s link libraries does not mutate the reusable option template. The DeviceTarget compile mode, which compiles a @cute.jit function as a device function for export, rejects link-libraries; cuda.coop.cutlass targets the default host-plus-kernel compilation.

Shared memory#

A CUB primitive’s TempStorage has a size and alignment that only the C++ compiler knows. Two routes exist. A wrapper can declare its own __shared__ storage in C++, which the device link lays out alongside the kernel’s shared memory; Warp Scan and other wrapper-owned storage use this. The deferred route, used wherever the caller may supply a TempStorage descriptor, traces placeholder arith.constant operands for the address and size, learns the exact layout from the same NVRTC program through nvrtcAddNameExpression and nvrtcGetLoweredName, and then inserts a SmemAllocator().allocate(size, alignment) at the kernel’s entry block and replaces the placeholders. SmemAllocator is stateless: it emits cute.memref.alloca operations that the compiler lays out together with the user’s allocations, and the launch reads the total through cute.kernel_smem_size. See Scratch allocation after tracing.

Barriers are emitted inside the wrappers, as __syncthreads() or a masked __syncwarp(), so the kernel’s IR contains no barrier operations for them. Group queries and group synchronization lower to small wrappers over cuda::hierarchy and the CUDA barrier intrinsics.

What we deliberately avoid#

cuda.coop.cutlass defines no MLIR dialect, adds no passes to the compile pipeline, and does not generate CuTe IR for the CUB algorithms themselves. The integration surface is the trace-time Python call, the FFI, the finalize hook, the link attribute, and the shared-memory allocator. Keeping to those means a CUTLASS release can change its internal lowering without affecting the generated CUB code.

Private interfaces we depend on#

Several of these facilities are private or new in the 4.9 candidate. Their names begin with an underscore or appear only in the candidate’s sources. _compiler/_runtime.py checks for them at import and reports which are missing, and the installed package is tested against the candidate:

  • cutlass.cutlass_dsl.CuTeDSL._get_dsl, register_trace_finalize_hook, and trace_finalize_hooks.

  • cutlass.cute._get_launch_facts and its cutlass_launch_facts schema in cutlass_dsl/_launch_facts_metadata.py.

  • cutlass.base_dsl.compiler.LinkLibraries with the link-libraries option name, and GPUArch.

  • cutlass.base_dsl.common.get_current_env_manager to check that a trace released its environment.

  • The MLIR bindings: ir.InsertionPoint.at_block_begin, ir.Value.replace_all_uses_with, the arith and llvm dialects, cute.Pointer.to_llvm_ptr, and SmemAllocator.allocate.

When a CUTLASS release changes one of these, expect the failure at import or at the first compilation rather than at runtime, and start with validate_cutlass_runtime and the lifecycle tests named in Developer Guide. The FAQ lists the other reasons a successful import can still fail to compile.

Vocabulary#

Term

Meaning in this documentation

trace

One execution of a @cute.jit function with symbolic arguments, producing one MLIR module. A kernel is traced inside its launch.

module, gpu.module, kernel operation

The builtin.module for a trace; the gpu.module holding its kernels; the lir.func or cuda.kernel operation for one kernel.

staged control flow

An if, for, or while rewritten by the preprocessor to emit scf operations because its condition or bounds are DSL values.

provider

A generated extern "C" C++ device function that calls CUB on behalf of one planned primitive call.

provider request

The record describing one provider: its plan, dtype, symbol name, and the C++ renderer that emits it.

bundle, session

The C++ translation unit containing all providers of one trace, and the per-trace object that collects requests and scratch uses for it.

trace-finalize hook

The DSL callback that runs after tracing and before module hashing; cuda.coop.cutlass compiles the bundle there.

deferred scratch

Shared memory whose placeholder operands are traced first and replaced after NVRTC reports the C++ layout.

link library

A file named in a gpu.module’s link-libraries attribute that the device link consumes; for us, the bundle’s LTO-IR.
